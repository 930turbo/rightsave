RightSave

Payments, without a billing server.

The implementation uses Lemon Squeezy hosted checkout and its public License API. There is no merchant API key, payment SDK, remotely loaded script or card form in the extension. The public release builds as Free; merchant configuration is an explicit build option.

Studio$49 once, 10 browser activationsAll Pro tools, portable workflow packs and CSV/JSON source records inside ZIPs.

These are draft launch terms, not active offers. One browser profile uses one activation. Studio supports a small team sharing a license; it does not include an online team dashboard or cloud sync. Avoid promising lifetime compatibility or updates. Define update/support and refund terms before opening sales. Leave recurring plans for a future product with recurring service costs.

Why this model

Raindrop keeps everyday bookmarking free and charges for advanced organization and archival tools; its billing runs through a hosted provider. Loom separates a free starter product from paid work and team capabilities. RightSave follows that useful division while using one-time licenses for its local tools. The payment provider is our implementation choice, not a claim that those products use it.

Set up a test store

  1. Create a Lemon Squeezy account and keep the dashboard in test mode. No real card details belong in payment testing.
  2. Create a RightSave product with separate Pro and Studio variants. Enable license generation, no expiry, and activation limits of 3 and 10 respectively. Set each variant to a one-time price. The provider enforces these limits; the extension does not infer them from its UI.
  3. Use each variant’s original Share checkout link containing /checkout/buy/. Never copy a customer’s single-use ?cart= URL.
  4. Copy billing.example.json outside the repository. Replace the placeholder store, product and variant IDs and checkout URLs with the test-store values. Keep testMode: true. This file contains public identifiers only.
  5. Build both browsers with node scripts/build.mjs --billing /absolute/path/to/billing.json. Install the test build in a disposable profile. The plans page labels both checkout links as tests.
  6. Complete checkout with the provider’s documented test card. Paste the receipt’s license key into RightSave. Check that the correct tier activates.

What the code does

Activation preflights the key against the configured store, product and variant before consuming an activation. It then calls /v1/licenses/activate with a random instance label. Validation uses the returned instance ID and checks the key, active status, expiry, store, product and variant. A Pro variant cannot unlock Studio. No customer name or email is retained.

License operations run in the extension background and are serialized. Successful checks are cached for up to 24 hours in that background session; a new session checks again. Network failures and rate limits allow at most seven days from the last successful check, bounded by license expiry. Invalid, disabled or mismatched responses clear paid access. A failed deactivation keeps the instance so it can be retried; a successful one releases it before removing the local key. The free features continue throughout.

For receipts and purchase recovery, the plans page links to Lemon Squeezy My Orders. It does not claim to manage subscriptions, since these products do not renew. If a browser profile is lost, the merchant can deactivate its instance in the dashboard after verifying the purchase.

Refunds and chargebacks

Handle refunds in the merchant dashboard and explicitly disable the corresponding license there. Verify that action as part of support handling; this integration does not assume every provider refund or chargeback disables a license automatically. The extension observes disabled status on its next online check. Existing offline access may last until the seven-day grace period ends. An automatic webhook-based revocation service is not deployed or required by this local integration.

Before opening sales

  • Approve the final prices, activation counts, upgrade policy, refund terms and support contact.
  • Activate the merchant store with the provider. Copy products to live mode and use the resulting live IDs and Share links in a separate config with testMode: false. Test and live product identifiers must not be mixed; the build flag labels the mode but cannot inspect your merchant dashboard.
  • Verify both variant activation limits, wrong-product rejection, repeated activation without duplicate seats, deactivation, disabled and expired licenses, offline grace and purchase recovery. The checked-in tests use a fake provider; they do not certify a live merchant checkout.
  • Complete a real merchant-controlled end-to-end purchase and refund before distributing a paid build. Confirm the receipt email, taxes, price, license delivery and the disabled-key response after refund handling.
  • Review the paid build’s browser privacy declarations, store listings and privacy notice. Publish signed/store-approved packages and keep the public local release Free.

Source-only local licensing can be modified by the person running it. This is an entitlement mechanism, not tamper-proof DRM. A future service would need server-side authorization for its own paid operations.
